# Path Pilot — premium payments and student enrollment

Updated 3 October 2026. All student features now require an active subscription; unpaid accounts have feature previews only. This is the complete MEAN application, based on the Vercel edition, with two additions requested for the software engineering lab: a premium-plan payment integration and a persistent enrolled-student register.

## What you can demonstrate

| Student workspace | Administrator workspace |
| --- | --- |
| Registration creates a persistent enrollment ID | Search enrolled students by name or email |
| One subscription unlocks profiles, learning, goals, quizzes, analytics and guidance | View enrollment date, college, degree and year |
| Razorpay test checkout for Premium | Filter preview-only/subscribed students with pagination |
| Verified payment activates time-limited access | Review payment references, status and access expiry |
| Four-week learning roadmap based on saved progress | Access is restricted to administrators |
| Download a career-progress CSV report | Test payments are clearly distinguished from real revenue |
| Payment history and status-recovery button | Student passwords and payment secrets are never shown |

“Enrolled student” means a registered student of this system in this version. Course-by-course enrollment is not included. MongoDB already stored accounts and progress; this update adds dedicated `enrollments` and `payments` collections linked to each student.

The provisional demo offer is **INR 499 for 30 days**, paid once, without automatic renewal. These are editable example settings, not confirmed commercial pricing. The initial gateway is **Razorpay test mode**, chosen for the Indian college context. If your payment-account country differs, confirm provider eligibility before creating the account; a currency setting alone does not change merchant eligibility.

**Test keys only. No real money is charged.** In Razorpay mode, checkout stays disabled until your own test credentials are configured; it never substitutes a fake success screen. The build rejects live Razorpay keys. In Razorpay mode, premium access is granted only after backend verification of the provider's captured payment, exact order, amount and currency.

## 1. Open the new project

Extract `Path_Pilot_Premium_Enrollment.zip` and open its `path-pilot-premium` folder. Keep this folder's `package.json`, `vercel.json`, `api`, `server` and `client` together.

Install Node.js **24.x**. In a terminal inside that folder:

```text
npm ci
npm run setup
```

If PowerShell blocks `npm.ps1`, use `npm.cmd` for the commands. The setup command creates `.env` with a random session secret; it preserves an existing `.env`.

## 2. Connect MongoDB and prepare accounts

Use your existing MongoDB Atlas database to preserve students and test results. If starting fresh, create an Atlas **Free/M0** cluster, a database user with `readWrite` access to `path_pilot`, and copy the connection URI. Set `.env`:

```dotenv
MONGODB_URI=mongodb+srv://YOUR_USER:YOUR_ENCODED_PASSWORD@YOUR_CLUSTER.mongodb.net/path_pilot?retryWrites=true&w=majority
NODE_ENV=development
COOKIE_SECURE=false
DEMO_PASSWORD=your-own-student-password
ADMIN_PASSWORD=a-different-admin-password
```

Use Atlas's actual hostname and URL-encode special characters in the database password. Keep the random `JWT_SECRET` generated by setup. Student/admin passwords must differ, be at least 10 characters, and fit in 72 UTF-8 bytes.

For a **new database**, run:

```text
node deploy/provision.mjs
```

This creates questions, sample progress and the two demo accounts:

- Student: `student@pathpilot.local` / your chosen `DEMO_PASSWORD`
- Admin: `admin@pathpilot.local` / your chosen `ADMIN_PASSWORD`

For an **existing populated database**, run only:

```text
node deploy/migrate-enrollments.mjs
```

The migration creates missing enrollment records without changing passwords, profiles, attempts or existing enrollments. It is safe to repeat. New registrations create their own enrollment immediately; older students also receive a missing record when their billing page or admin directory entry is read.

Do not re-run provisioning merely to upgrade: it explicitly reapplies the two demo account passwords. Never delete the existing database for this update.

For local MongoDB instead of Atlas, use `mongodb://127.0.0.1:27017/path_pilot`, start MongoDB first, and use the same provisioning or migration steps. The original local-development notes are in `docs/LOCAL_SETUP.md`.

## 3. Configure Razorpay test checkout

1. Create/sign in to a Razorpay account eligible for your country, and switch to **Test Mode**.
2. Generate a test API key pair in the dashboard. The key ID must begin with **`rzp_test_`**.
3. Choose a separate random webhook signing secret with at least 16 characters. It is different from the API key secret.
4. Add these values to your local `.env` and, when hosted, to Vercel's server environment variables:

```dotenv
RAZORPAY_KEY_ID=rzp_test_your_key_id
RAZORPAY_KEY_SECRET=your_test_api_key_secret
RAZORPAY_WEBHOOK_SECRET=your_separate_random_webhook_secret
PREMIUM_PRICE_PAISE=49900
PREMIUM_DAYS=30
```

`49900` paise = INR 499. This build uses INR; change the amount and duration as needed. Allowed ranges: 100–10000000 paise and 1–366 days. Existing orders retain their original price/duration; configuration changes apply to new orders. Keep the same gateway key pair while pending orders exist.

All three Razorpay fields may be empty while configuring the project. A partial configuration is rejected. Do not put the secret key in Angular code, GitHub, screenshots, or a public environment variable. Only the public key ID and order details reach checkout. Do not paste keys into chat.

5. Enable **automatic capture** in Razorpay's payment capture settings. An authorized-but-not-captured payment does not activate Premium.
6. In Razorpay **Test Mode → Webhooks**, add the deployed HTTPS endpoint:

```text
https://YOUR-PROJECT.vercel.app/api/billing/webhook
```

Use the same `RAZORPAY_WEBHOOK_SECRET`. Subscribe to:

- `payment.captured`
- `payment.failed`
- `order.paid`
- `refund.processed`

The URL must be publicly reachable without a Vercel login page. For local development, Razorpay cannot reach `localhost` directly. You can still exercise checkout callback verification and **Check status** locally; use the deployed URL for provider webhook delivery.

7. Use the test payment details in Razorpay's current documentation, never real card details. Test success, failure and dismissal. Test-mode availability and payment methods depend on your account; this package cannot create or activate an account for you.

Official references: [Checkout integration and test payments](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/), [webhook signature validation](https://razorpay.com/docs/webhooks/validate-test/).

## 4. Run locally

After configuring `.env` and your database:

```text
npm run build
npm start
```

Open **http://127.0.0.1:3000**. For active development, `npm run dev` runs the Angular development server and Express API; open **http://localhost:4200**.

Sign in as a student and select **Subscription & payments**. Sign in as admin to find **Enrolled students** and **Payments**.

Upload the extracted project's source files to your GitHub repository. Do not upload the ZIP itself, `.env`, `node_modules`, or test output. Keep `package.json` and `vercel.json` at the repository root. Preserve existing deployment secrets in Vercel.

| Setting | Value |
| --- | --- |
| Root Directory | Repository root, not `client` |
| Framework Preset | Other |
| Node.js | 24.x |
| Install command | `npm ci --include=dev` |
| Build command | `npm run build` |
| Output Directory | `client/dist/path-pilot/browser` |

The supplied `vercel.json` provides the build settings, routes and checkout-compatible security headers. No Docker or separate backend host is required.

Set these server environment variables for **Production** (and Preview only if needed):

```dotenv
MONGODB_URI=your-full-Atlas-URI
JWT_SECRET=your-existing-or-generated-random-secret-of-at-least-32-characters
NODE_ENV=production
COOKIE_SECURE=true
ENABLE_EXTERNAL_QUIZZES=false
RAZORPAY_KEY_ID=rzp_test_your_key_id
RAZORPAY_KEY_SECRET=your_test_api_key_secret
RAZORPAY_WEBHOOK_SECRET=your_separate_random_webhook_secret
PREMIUM_PRICE_PAISE=49900
PREMIUM_DAYS=30
```

Use the same Atlas database you migrated. Keep your existing JWT secret to preserve valid sessions. Redeploy after changing environment variables. Configure the Razorpay test webhook after obtaining the public production URL.

Atlas Network Access must allow your laptop for provisioning/migration and Vercel for API requests. Vercel's standard outbound IP addresses are dynamic. For a classroom-only database, the temporary Atlas rule `0.0.0.0/0` allows connections from any IP; use a strong database-scoped password and sample data, and remove the broad rule after retiring the demo. See [Vercel outbound networking](https://vercel.com/kb/guide/how-to-allowlist-deployment-ip-address). More baseline deployment details are in `deploy/VERCEL_GUIDE.md`.

## 6. Presentation checklist

1. Register a student or use the sample student. Show their enrollment number and Preview only status.
2. Explore the feature descriptions. Open a direct test or guidance URL to show that it returns to the preview until subscribed.
3. Open **Subscription & payments**, show the price and duration, and choose **Subscribe with test payment**.
4. Complete a successful Razorpay test payment. Show Premium, its expiry date, the four-week roadmap and the CSV download.
5. Reload or sign out/in to show database persistence.
6. Sign in as admin. Search for the student under **Enrolled students**, filter Premium, then show the matching paid record in **Payments**.
7. Use a second unsubscribed student to demonstrate a failed or dismissed checkout. Their access remains preview-only. A pending order can be retried.
8. Check Razorpay's webhook delivery log for an HTTP 200 response. Re-send the event to demonstrate that the expiry date does not extend.

If a callback is missed, the student can use **Check status** beside the payment. Browser success text or query parameters alone never unlock access.

## Database and payment behavior

- `users`: identity, email, role and password hash.
- `profiles`: academic details, skills, topics and goals.
- `enrollments`: one stable enrollment number and enrollment date per student.
- `payments`: owner, gateway order/payment references, amount in paise, currency, duration, test mode, status and access dates.
- `questions` / `attempts`: existing practice content and results.

Payment states are `creating → pending → paid`, with `failed` for order-creation failure and `refunded` when a processed refund is confirmed. A failed attempt inside an existing checkout leaves the order pending, records the failure time and allows retry. Dismissing checkout does not falsely mark a payment as failed or paid.

Only one open order is allowed per student. Price and duration come from the server. The server verifies callback HMAC signatures using its stored order ID, checks webhook HMAC signatures against the original bytes, and fetches the provider's current payment state before activation. Amount, currency, order and student ownership must match. An atomic status transition makes repeated or concurrent notifications safe. Access expires automatically by date; there is no scheduled job to run. Purchase again after expiry for a new term.

The demo policy revokes access for any processed refund, including partial refunds. This app does not initiate refunds; use the provider's test dashboard and let its webhook update the record. A late capture notification cannot restore a refunded purchase.

No card number, CVV, bank password or payment secret is stored in MongoDB. The backend does not log provider response bodies. Public accounts start with preview-only access; no paid membership is seeded. Explicit simulation mode provides an authenticated demo-outcome endpoint for classroom demonstrations; Razorpay mode disables it.

## Verification and limitations

See `docs/PREMIUM_TEST_REPORT.md` for the exact local results. Payment tests use a deterministic provider fixture and a real isolated MongoDB process. Browser tests intercept the external checkout script to exercise success/dismissal and then use the real application verification endpoints with signed fixture responses. These tests do **not** prove that your gateway account or Vercel deployment is configured correctly.

No payment account was created, no real money was charged, and no deployment was made to your account. You must add your own test keys and complete a real provider **test-mode** transaction plus a deployed webhook delivery check before presenting the gateway as connected.

The prototype deliberately supports one fixed-term plan, INR, test payments and manual repurchase. Recurring subscriptions, live billing, tax invoices and refund initiation are outside this update. Rate limiting remains per application instance; internet-scale deployment needs shared rate limiting and production operational review. Your later requested improvements can be added to this version.

## Troubleshooting

| Problem | Action |
| --- | --- |
| Upgrade button disabled | Add all three Razorpay test settings, restart/redeploy, then refresh |
| API returns 503 after setting keys | Check that key ID starts `rzp_test_`, all secrets are present, webhook secret is 16+ characters, and the amount/duration are valid |
| Checkout script fails to load | Check connectivity/browser blockers and retain the supplied security headers |
| Payment authorized but Premium inactive | Enable automatic capture; then use Check status or wait for the capture webhook |
| Payment completed but page did not update | Use Check status on the corresponding order, then refresh membership |
| Webhook returns 400 | Check the webhook signing secret, Test Mode, correct endpoint and unmodified raw body; do not replace this route with a JSON-parsed handler |
| Webhook asks for Vercel login | Use an unprotected public production deployment |
| Old student lacks a record | Run `node deploy/migrate-enrollments.mjs` against the deployed database |
| Plan price changed but old checkout shows previous price | Pending orders keep their original price; new orders use the new setting |
| Failed checkout appears Pending | It is an order still available for retry; a failed attempt is noted separately |
| Checkout temporarily says it is being prepared | Wait and retry; a stopped creation attempt can be cleared on retry after 60 seconds |
| Changing currency is needed | This edition uses INR; changing the currency requires reviewing provider support and minor-unit handling |
